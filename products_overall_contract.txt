1. COMO O ENDPOINT FUNCIONA
---------------------------------------------------------------------
Assinatura atual do controller:

    @GetMapping("/overall")
    public ResponseEntity<ProductPageResponseDto> getProductPage(
            @PageableDefault(size = 20, sort = "name",
                             direction = Sort.Direction.ASC)
            Pageable pageable,
            ProductFilterDto filter)

ProductFilterDto (record; bind via query params, @ModelAttribute implicito):

    public record ProductFilterDto(
            String category,        // aceito, porem IGNORADO pelo service
            Marketplace marketplace,
            Boolean hasListings,
            StockFilter stock,      // LOW | OUT | NORMAL
            String searchTerm
    )

Regras gerais:
  - Todos os filtros sao OPCIONAIS e COMBINAVEIS entre si e com
    page/size/sort.
  - Omitir todos os filtros comporta-se como na versao sem filtros.
  - Sempre aplicado (nao configuravel): produto pertence ao tenant do
    token AND active = true.


2. PARAMETROS DE ENTRADA (todos via QUERY STRING; nunca via body)
---------------------------------------------------------------------
Param        Tipo      Default    Descricao
page         int       0          Numero da pagina (0 = primeira).
                                  Pagina fora da faixa -> 200 com
                                  items: [] e hasNext: false.
size         int       20         Itens por pagina.
sort         campo,dir name,asc   Ordenacao; repetivel:
                                  ?sort=sales,desc&sort=name,asc
                                  (a primeira tem prioridade, a segunda
                                  desempata). Sem direcao -> asc.
                                  Campo inválido -> 400 (secao 5b).
searchTerm   string    -          Busca case-insensitive por name OU sku
                                  (LIKE %termo%). Complementos:
                                  - se o termo contiver o nome de um
                                    marketplace (ex.: "shopee",
                                    "mercadolivre"), tambem inclui
                                    produtos com listing naquele
                                    marketplace (EXISTS subquery)
marketplace  enum      -          SHOPEE | MERCADOLIVRE (maiusculas)
                                  Produto possui no minimo 1 listing
                                  nesse marketplace (EXISTS).
hasListings  boolean   -          true  -> so produtos COM listings
                                  false -> so produtos SEM nenhum listing
stock        enum      -          LOW    -> stock <= min_stock AND
                                            stock > 0  (estoque baixo)
                                  OUT    -> stock <= 0            (zerado)
                                  NORMAL -> stock > min_stock   (saudavel)
                                  (min_stock default do banco = 20;
                                   NAO e filtro por quantidade exata)
category     string    -          PRESENTE no DTO, porem o service
                                  NUNCA usa. Nao gera erro: e descartado.
                                  NAO criar filtro de categoria no UI
                                  ate o campo ser implementado.

Valores validos sao CASE-SENSITIVE nos enums (ver secao 5):
  marketplace deve ser "SHOPEE"/"MERCADOLIVRE"; stock deve ser
  "LOW"/"OUT"/"NORMAL". hasListings aceita true/false (TRUE/FALSE e
  ate case-insensitive: FALSE e TrUe testados, todos 200).

Resultados medidos nos dados atuais de teste (50 produtos MOCK-001..050,
300 listings; consultar apenas como referencia, variam com os dados):
  ?searchTerm=mock+product+0                -> 9 resultados
  ?searchTerm=shopee                        -> 50 (case-insensitive;
                                               filtra via nome do enum)
  ?marketplace=SHOPEE                       -> 50
  ?hasListings=false                        -> 1
  ?stock=LOW / OUT / NORMAL                 -> 20 / 0 / 31
  combinado LOW+SHOPEE+hasListings+termo    -> funcionou (200)

Exemplo de requisicao completa:

  GET /api/products/overall
      ?page=0&size=20&sort=name,asc
      &searchTerm=mock&marketplace=SHOPEE&hasListings=true&stock=LOW
  Authorization: Bearer <accessToken>


3. CAMPOS VALIDOS PARA sort
---------------------------------------------------------------------
O service consulta via findAll(spec, pageable), portanto vale qualquer
propriedade da entidade Products — nomes Java em camelCase, nunca nome
de coluna do banco:

  publicId, sku, name, stock, baseSellPrice, costPrice, imageUrl,
  sales, createdAt, updatedAt, minStock, active

Formato: sort=<campo>,<asc|desc>

NAO ordena (campos derivados/calculados apos o service):
  listingCount  -> ?sort=listingCount,desc devolve 400 hoje (secao 5b)
  category

Erros comuns que o frontend nao deve cometer:
  base_price, updated_at, total_sales  -> nomes de coluna do banco:
                                          geram 400 (ver secao 5b)
  Sempre usar a propriedade Java exata (baseSellPrice, updatedAt...).

  - createdAt/updatedAt no formato yyyy-MM-dd'T'HH:mm:ss.

    (uppercase). Marketplace ausente => contador zero (nao vira chave

      stock <= 0        -> OUT
      stock <= minStock -> LOW
      otherwise         -> NORMAL
    Hoje todos os produtos tem minStock = 20 (default da coluna; o
    cadastro por API ainda nao aceita valor custom), mas o badge deve
    usar o campo, nao constante, para acompanhar produtos futuros.


5. ERROS QUE O FRONTEND DEVE TRATAR
---------------------------------------------------------------------
a) Valor fora do enum / booleano invalido -> HTTP 400

   Envelope (capturado em 06/11/2026):

   {
     "detail":   "Invalid Request, please verify the following fields
                  and try again",
     "instance": "/api/products/overall",
     "status":   400,
     "title":    "Invalid Request",
     "type":     "/Errors/Validation",
     "errors":   [ "Valor inválido para '<campo>'. Valores aceitos:
                    <lista>." ]
   }

   Mensagens exatas por campo:

   ?marketplace=NOPE   -> "Valor inválido para 'marketplace'.
                           Valores aceitos: SHOPEE, MERCADOLIVRE."
   ?stock=MEDIUM       -> "Valor inválido para 'stock'.
                           Valores aceitos: LOW, OUT, NORMAL."
   ?hasListings=xyz    -> "Valor inválido para 'hasListings'.
                           Valores aceitos: true, false."

   Regras confirmadas por teste:
     - Enums sao CASE-SENSITIVE: stock=low, stock=Low e
       marketplace=shopee geram o mesmo 400.
     - hasListings aceita true/false, TRUE/FALSE e case-insensitive
       (FALSE e TrUe testados, todos 200).
     - A rejeicao acontece no bind do DTO: nenhum filtro parcial e
       aplicado; o service nunca chega a executar.
     - Como detectar: type == "/Errors/Validation". O campo rejeitado
       esta entre aspas simples em errors[0] ('marketplace', 'stock')
       e a lista de valores aceitos vem apos "Valores aceitos:"
       (separada por ", "). A mensagem pode ser exibida direto ao
       usuario sem parse adicional.
     - Fonte no backend: ApiExceptionHandler converte bind failures em
       mensagens "Valor inválido para '<campo>'..." a partir do tipo
       do campo (enum -> lista de constantes; Boolean -> true/false).

b) sort com campo inexistente ou derivado -> HTTP 400 (corrigido
   pos-restart; handler propria para PropertyReferenceException)

   Envelope:

   {
     "detail":   "Invalid Request, please verify the following fields
                  and try again",
     "instance": "/api/products/overall",
     "status":   400,
     "title":    "Invalid Request",
     "type":     "/Errors/Validation",
     "errors":   [ "Campo de ordenação inválido: '<campo>'." ]
   }

   Casos testados:

     ?sort=nome_banana,asc    -> "Campo de ordenação inválido: 'nome'."
     ?sort=listingCount,desc  -> "Campo de ordenação inválido:
                                  'listingCount'."
     ?sort=base_price,asc     -> "Campo de ordenação inválido: 'base'."
                                  (nome de coluna do banco rejeitado)

   Detalhes confirmados em teste:
     - O campo reportado e a BASE da propriedade: nomes com "_"
       reportam apenas o primeiro segmento (nome_banana -> 'nome';
       base_price -> 'base'). Tudo e rejeitado com 400.
     - Excecao rara: valores que nao sao identificadores simples
       (ex.: sort=root.get("name"),asc) escalam para 500 Internal
       Server Error com corpo {"timestamp", "status": 500, "error":
       "Internal Server Error", "path"}. Nao usar esse tipo de payload;
       strings invalidas "normais" sempre caem no 400 acima.
     - Historico deste caso: 401 mascarado 502->401 quando /error
       estava bloqueado; depois 500 quando /error foi liberado; hoje
       400 via handler dedicado no ApiExceptionHandler.

c) 401 generico (body vazio): token ausente/expirado -> renovar pelo
   fluxo de refresh token do backend e repetir a requisicao original.


6. SUGESTAO DE TYPES (TypeScript) PARA O FRONTEND
---------------------------------------------------------------------
type Marketplace = "SHOPEE" | "MERCADOLIVRE";
type StockFilter = "LOW" | "OUT" | "NORMAL";
type ProductSortField =
    "publicId" | "sku" | "name" | "stock" | "baseSellPrice"
  | "costPrice" | "sales" | "createdAt" | "updatedAt" | "minStock";

interface ProductListQuery {
  page?:        number;
  size?:        number;
  sort?:        `${ProductSortField},${"asc" | "desc"}`; // repetivel
  searchTerm?:  string;
  marketplace?: Marketplace;
  hasListings?: boolean;
  stock?:       StockFilter;
  // category: NAO enviar (ignorado pelo backend hoje)
}

interface ListingCount { SHOPEE?: number; MERCADOLIVRE?: number; }

interface ProductResponse {
  publicId:      string;
  sku:           string | null;
  name:          string;
  stock:         number;
  minStock:      number;   // limite individual p/ badge (hoje sempre 20)
  baseSellPrice: number;
  costPrice:     number;
  imageUrl:      string | null;
  sales:         number;
  createdAt:     string;   // yyyy-MM-dd'T'HH:mm:ss
  updatedAt:     string;
  listingCount:  ListingCount;
}

// Derivacao do badge de estoque (mesma regra do filtro):
//   stock <= 0 -> "OUT" | stock <= minStock -> "LOW" | senao -> "NORMAL"

interface ProductPageResponse {
  items:       ProductResponse[];
  actualPage:  number;
  totalPage:   number;
  totalItems:  number;
  pageSize:    number;
  hasNext:     boolean;
}


7. RESUMO PARA MONTAGEM DE UI
---------------------------------------------------------------------
- Busca unica                    -> searchTerm
- Chips de marketplace           -> marketplace (SHOPEE/MERCADOLIVRE)
- "Somente publicados"           -> hasListings=true
- "Nunca publicados"             -> hasListings=false
- Estado de estoque              -> stock (LOW/OUT/NORMAL, maiusculas)
- Filtrar por categoria          -> NAO suportado (nao enviar)
- Ordenar por listingCount       -> NAO suportado (evitar; hoje = 400)
- Paginacao/ordenacao            -> page/size/sort (padrao Pageable do
                                    Spring; sort repetivel)
